# HTTP API

The routes of the KIPscope server (default `http://127.0.0.1:7310`), for your own client or to connect KIPscope to other tools. The UI and the CLI use the same routes; the CLI reference is in the [README](../README.md#cli). Payload types live in `packages/shared/src`; each route's fields, answers and errors are in the spec named in the table. Data sources: [data-sources.md](data-sources.md).

## Shared rules

- **Host and Origin** ([server-access](../openspec/specs/server-access/spec.md)): a request is answered only when its `Host` names `localhost`, `127.0.0.1` or `[::1]` (any port), the configured non-loopback `KIPSCOPE_HOST`, or the host of a `KIPSCOPE_ORIGINS` entry; otherwise 403 `forbidden_host`. A request with an `Origin` must be `http`/`https` with a loopback host or the `KIPSCOPE_HOST` name, or exactly one of `KIPSCOPE_ORIGINS`; otherwise (`null` included) 403 `forbidden_origin`. Requests without `Origin` (curl, the CLI) pass. The live channel's upgrade follows the same rules.
- **Identity** ([user-identity](../openspec/specs/user-identity/spec.md), [deploy.md](deploy.md)): with `KIPSCOPE_IDENTITY=none` (the default) every request is the user `local`, every workspace is granted everything, and nothing below needs a credential. Otherwise the identity adapter checks every `/api/` request but `GET /api/license`, the live upgrade included: no credential answers 401 `unauthenticated`, a bad one 401 `invalid_token`, an adapter that cannot decide (IdP unreachable) 503 `identity_unavailable`. With `oidc` the credential is `Authorization: Bearer <JWT>` (or the header `KIPSCOPE_OIDC_HEADER` names).
- **Access levels** ([data-access](../openspec/specs/data-access/spec.md)): every route declares one, checked in this order before the route runs. `public`: no user. `user`: a signed-in user. `workspace`: also the open right on the workspace, else 403 `forbidden`. `change`: also the change right, else 403 `read_only`. Then every data ref the request names (`signal`, `dataRef`, a command's signal or scope, a view's data refs) must be covered by the workspace's grant, else 403 `forbidden_data` with the message `data ref <ref> is not permitted`; for `POST /api/workspaces {open}` that is the grant the new workspace will get. That answer is decided from the grant alone, before any lookup or source query, so it is the same for a data ref that exists and one that does not. Lists and counts (catalog, `/api/signals` `total`, meta `size`) never include data refs outside the grant, and `/api/workspaces` never lists other users' workspaces.
- **Grant** ([deploy.md](deploy.md#rights)): each workspace holds the data refs it may read, decided by the search tool (finder). With `none` it is everything; on a server a new workspace's grant is empty until a handoff from the search tool widens it. No request sets a grant; a client only reads `granted` (`"all"` or the number of data refs) in the workspace summary.
- **JSON bodies:** request bodies are `application/json` only; any other type, `text/plain` included, gets 415. A POST without a body is fine. Bodies up to 1 MiB (Fastify's default, else 413), `POST /api/workspaces` up to 4 MB for a catalog; a view text for import at most 256 KiB (413 `view_too_large`); a live channel message at most 256 KiB (the connection closes with 1009).
- **Times** are decimal nanoseconds since 1970-01-01T00:00:00Z as strings (`"1791158400000000000"`), in answers and in query fields; query fields also accept ISO-8601 (`2026-10-05T00:00:00Z`). Bounds lie within 1900-01-01 … 2262-04-11.
- **Signal IDs** are `<dataRef>/<name>`, e.g. `smart451/BMS.SOC`; URL-encode them in query strings. A computed signal is `<dataRef>/=<id>`, e.g. `smart451/=c7` (see "Computed signals" below).
- **Errors** answer `{"error": {"code": "...", "message": "..."}}`, sometimes with more fields (`signalId`, `reason`, the range). 400 `invalid_request` for a bad query or body; 404 for an unknown signal, data ref or view; 502 `source_error` when the database query failed.
- **Too wide** ([scope](../openspec/specs/scope/spec.md) "Scan bound", D-117): KIPscope never scans a source's whole data. Before a call that reads every row of a data ref in a range, the server checks the range against `KIPSCOPE_SCAN_SPAN` (default `7d`, refused with no query) and then `KIPSCOPE_SCAN_ROWS` (default 150,000,000 rows, one shared count per range, kept 5 min). A refused range answers 422 `too_wide` on `/api/density`, `/api/gaps`, `/api/series`, `/api/value`, `/api/events`, `/api/catalog` and `/api/signals`, within the time of that one count, never a timeout. The error carries `rows` and `limit` (decimal) when the row count decided, or `span` and `maxSpan` (decimal ns) when the span did, and the message `too wide: 230,000,000 rows, more than the 150,000,000 a query may read; choose a shorter range` or `too wide: 17 d is more than the 7 d a query may span; choose a shorter range` (`tooWideText` in `packages/shared`). `/api/meta` reports the bound as `limits`.
- **Catalog not loaded:** routes that need the signal catalog answer 503 `catalog_unavailable` with `reason` (still loading, or source unreachable) until the first load succeeded.
- **Scope** ([scope](../openspec/specs/scope/spec.md), D-078): the workspace may hold a scope, one data ref and a half-open time window `[from, to)`. While it does, every data route answers as if the source held only that window of that data ref: the catalog and signal search list the scope's signals (`scope` in the answer), density, gaps and events cover the scope, series ranges are cut to it, and every source query carries the data ref and both time bounds. A signal or `dataRef` of another data ref, a series range wholly outside, or a `value` time outside answers 409 `out_of_scope`. With `KIPSCOPE_CATALOG=scoped` (the default) and no scope, the catalog and data routes answer 409 `scope_required`, and `/api/meta` reports catalog state `no_scope`; the one exception is `GET /api/density` with `dataRef`, `from` and `to`, which runs with that window as its scope, bounded like any scan. `KIPSCOPE_CATALOG=full` (a start-up catalog of every data ref) is for small sources only; the scan bound holds there too, and data refs over it answer `too_wide`. The scope changes only through the commands `scope.set` and `scope.clear` and through opening a view (which sets the view's scope, else one derived from its windows, cursors and `KIPSCOPE_SCOPE_PAD`); loading the new scope's signal list first can answer 503 `catalog_unavailable`, or 422 `too_wide` when the scope is over the scan bound, with the workspace unchanged. Range commands are clamped into the scope (`clamped: true` in the result); commands refused for the scope (`scope_required`, `out_of_scope`) answer 422 like other rejected commands.
- **Commands** answer a `CommandResult` (`{ok: true, revision, …}` or `{ok: false, code, message}`): 200, 400 `invalid_command`, 503 `catalog_unavailable`, 403 `forbidden_data`, 502 `source_error` (a case command whose source query failed), else 422. `scope.set`, `view.open`, `case.go`, `case.step` and `case.link` whose target scope is over the scan bound answer 422 `too_wide` with the fields of "Too wide" (`rows`, `limit` or `span`, `maxSpan`) and leave the workspace unchanged.
- **Request class** ([case-preload](../openspec/specs/case-preload/spec.md), D-081): the header `X-KIPscope-Class: preload` on `GET /api/series`, `GET /api/extent`, `GET /api/calendar` and `GET /api/case/preview` runs the request's source work in the lowest query class, after every interactive, metadata and background query. Any other value, or the header on another route, is ignored: the request stays interactive.

## Workspaces

Each workspace ([workspaces](../openspec/specs/workspaces/spec.md)) has an ID of 10 characters `[a-z0-9]`, an owner, a share level (`private`, `read`, `write`), a grant and its own live channel. The UI page of a workspace is `/w/<id>`.

- **Prefix rule:** every route of access level `workspace` or `change` (table below) also answers as `/api/w/<id>/<rest>` for workspace `<id>`, e.g. `/api/w/abcdefghij/workspace` or the live channel `/api/w/abcdefghij/live`. An ID of the right form that names no workspace answers 404 `unknown_workspace`. On the other routes a prefix is ignored. The table names each route once, without the prefix. The old prefix `/api/s/<id>/…` is an unknown route (404).
- **Default workspace:** without the prefix, a `workspace` or `change` route serves the requester's default workspace: their own with the latest activity, or a new empty one when there is none. Scripts and the CLI without `--workspace` keep working this way.
- **Workspace header:** every answer that served a workspace carries `X-KIPscope-Workspace: <id>`; a client that wants to stay in one workspace takes it from the first answer and prefixes later requests (the CLI does).
- **Live channel:** on connect it sends `{type: "hello", clientId}`, then `{type: "summary", summary}` (the workspace summary with this connection's `rights`, `owner` and `granted`), then `{type: "state", …}`. After a share change, a grant change or a command it sends `summary` again when this user's rights or `granted` changed, or closes with code 4403 when the user lost the open right; deleting the workspace closes every connection with 4404. Clients do not reconnect after these two codes.
- **Favourites on the live channel:** when the server keeps favourites, right after the connect `state` it sends `{type: "favourites", names, error?}` of the connection's user, and again after every `POST /api/favourites` of that user that changed the list, from any tab, workspace or the CLI; a change that changes nothing sends nothing. Favourites are per user, never part of the workspace.
- **Reuse:** `POST /api/workspaces {reuse: true}` (what the UI sends for `/`) returns the requester's latest workspace that has no open tab and was not handed out in the last 10 s, with `reused: true`, else a new one; two tabs never get the same one. `reuse` and `open` together answer 400.
- **Sharing** never widens data access: an invited user sees the shared workspace's grant while in it, and their own workspaces never gain it. Only the owner may share or delete a workspace (else 403 `not_owner`); `read` and `write` need sharing turned on (`KIPSCOPE_SHARE=on`, the default; else 403 `share_not_permitted`). `GET /api/me` reports it as `canShare`. A user has at most 200 workspaces; creating one more removes the least recently active without an open tab, or answers 409 `workspace_limit`.

## Computed signals

A computed signal (`<dataRef>/=<id>`, defined in the workspace's `computed` list by the commands `computed.add`, `computed.update`, `computed.remove`) is read through `GET /api/series`, `GET /api/value` and `GET /api/extent` with one more query parameter ([computed-signals](../openspec/specs/computed-signals/spec.md)):

| Parameter | Meaning |
|---|---|
| `formula` | the flattened formula over source signals, at most 2,000 characters and 256 parts: signal names, numbers, `+ - * /`, parentheses, `abs(x)`, `min(x, y, …)`, `max(x, y, …)`; at least one and at most 8 distinct signal names. A name is a signal's full name without data ref (`MS_312h.DNMOT`), resolved exactly as `<dataRef>/<name>` on the computed signal's data ref; a name that is not an identifier is written in double quotes with `\` and `"` escaped by `\` (`"1st.X"`). The server knows no short names and no definitions: clients send the formula with nested computed signals replaced by their formulas. |

The server parses the formula itself and never puts request text into a query. Answers keep their shapes (`RawSeries`, `BucketSeries`, `CursorValueResult`, `Extent`) with `signalId` the computed ID. Rows lie at the inputs' point times, each input holding its last point for at most 3 of its periods; a row is SNA (`null`) when an input's held point is SNA or the result is not finite. A series is raw when the range holds at most `target` input rows, else buckets of the exact rows. An extent spans from the latest of the inputs' firsts to the latest of their lasts.

| Route | Errors |
|---|---|
| `/api/series` | 400 `invalid_request`: `a computed signal needs formula`, `formula goes with a computed signal only` (a plain signal with `formula`); 400 `invalid_formula` (the parser's message with its position, e.g. `Unexpected ")" at 20`, or `At most 8 signals (with nested ones): 9`); 404 `unknown_signal` (a name not in the list in use, `signalId` the input's ID, message `not in this list: <id>`); 422 `not_numeric_signal` (an input with states); 422 `computed_too_large` (a source without a native computed series: one cap of 200,000 rows for all n inputs together, split evenly, so more than `floor(200,000 / n)` rows of one input in the range fail with e.g. `more than 100,000 rows of MS_312h.DNMOT in this range: zoom in`) |
| `/api/value` | the same, without `computed_too_large` |
| `/api/extent` | the same, without `computed_too_large`; 404 `no_data` when an input has no data |

Example: `/api/series?signal=smart451%2F%3Dc8&formula=abs(MS_312h.DNMOT%20-%20CPC_508h.PNHV_SupBat_Curr)&from=…&to=…&target=2000`.

## Sessions from a finder

A search tool (finder; not part of KIPscope) hands over an ordered catalog of sessions (vehicle, `[from, to)`, kind, meta); [handoff.md](handoff.md) is the guide for its implementers, [case-handoff](../openspec/specs/case-handoff/spec.md) and [case-navigation](../openspec/specs/case-navigation/spec.md) the specs.

- **Open:** `POST /api/workspaces {open: {cases}}`, where `cases` is a JWS signed by the finder, an unsigned code (deflate-raw, base64url, as `#view=`) or, with identity `none`, the catalog document itself. With any other identity only a JWS that verifies against `KIPSCOPE_FINDER_JWKS` is accepted, and its user claim must be the signed-in user. Each open creates a new workspace, widens its grant by exactly the catalog's data refs (`KIPSCOPE_CASE_DATAREF`, default `{object}`), shows the current session (scope `[from − pad, to + pad)`) with the payload's view or the requester's latest workspace's windows, and answers `case: {count, current, dataRefs, missing, alignFallback?, warnings}`.
- **State:** the workspace's `case` holds `catalogId`, `count`, `current` (0-based), `linked`, `pad`, `align`, `alignAt` and the current `entry`; the entries are served by `GET /api/case` and survive a restart.
- **Commands** on `POST /api/commands`: `case.go {index}` (also links), `case.step {by: -1 | 1}`, `case.unlink` (the scope becomes the span of the catalog's sessions of that vehicle, padded, `object: true`, with no source query), `case.align {align: {mode: "start" | "end" | "anchor" | "event", event?}, at?}`. A step loads the target session's signal list first (503 `catalog_unavailable`, unchanged), keeps every window's offset from the alignment point and moves signals to another vehicle by name (`missing` in the result lists those it lacks; `alignFallback: true` when the session start replaced the mode). While a catalog is open, `scope.set` and `scope.clear` answer 422 `case_open`.
- **Object scope** (after `case.unlink`): gaps, events and the density need the work window as `from` and `to` (at most `KIPSCOPE_SCAN_SPAN`; there is no coarse density over the whole vehicle), and the signal list stays the last linked session's (`partial: true` in `/api/catalog`). The calendar answers from the vehicle-days with `pending`.

## Error codes of identity, grants and workspaces

| Status | Code | When |
|---|---|---|
| 401 | `unauthenticated` | no credential |
| 401 | `invalid_token` | a credential the adapter refused (bad signature, expired, wrong audience, …) |
| 503 | `identity_unavailable` | the adapter could not decide (IdP or its keys unreachable) |
| 403 | `forbidden` | no open right on the workspace (private to someone else) |
| 403 | `read_only` | the workspace is shared `read` to this user |
| 403 | `forbidden_data` | a named data ref the workspace's grant does not cover |
| 403 | `not_owner` | share or delete by someone other than the owner |
| 403 | `share_not_permitted` | `read` or `write` with `KIPSCOPE_SHARE=off` |
| 404 | `unknown_workspace` | a workspace ID of the right form that names no workspace |
| 409 | `workspace_limit` | 200 workspaces, each with an open tab |
| 409 | `grant_limit` | a catalog would grant the workspace more than 2,000 data refs |
| 400 | `invalid_catalog` | a catalog that is no catalog document (the message names the first bad path), longer than 4,000,000 characters, or inflating to more than 4,194,304 bytes |
| 403 | `signature_required` | an unsigned catalog with an identity other than `none` |
| 403 | `invalid_signature` | a catalog JWS that does not verify; `reason` one of `bad_signature`, `unknown_key`, `algorithm`, `expired`, `not_yet_valid`, `lifetime`, `issuer`, `audience`, `malformed` |
| 403 | `wrong_user` | a catalog signed for another user |
| 404 | `no_case` | a case route in a workspace without a catalog |
| 503 | `finder_not_configured` | a catalog open with an identity other than `none` and no `KIPSCOPE_FINDER_JWKS` |
| 503 | `finder_keys_unavailable` | the finder's key set could not be read or fetched and never loaded |
| 422 | `no_case`, `case_end`, `case_unlinked`, `case_open`, `no_matching_event` | a case command refused: no catalog; past the first or last session; while unlinked; `scope.set`/`scope.clear` with a catalog open; event alignment without a match in the session |
